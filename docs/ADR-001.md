# ADR-001: Transition from a Static Site to a Containerised SSR Runtime

## Status

Accepted (Date: 2026-10-07)

## Context

The site is currently a static Astro build. Every page is rendered to HTML at
build time and served from S3 through CloudFront. Any change, including a new post,
needs a rebuild locally and a redeploy.

The site is moving towards regularly published content: a weekly news roundup now,
and an automatically generated daily brief later. It also needs server-side
endpoints. `/api/health` lets a container platform check the app is alive, and
`/api/feedback` accepts input from readers.

S3 can only serve files. It cannot compute server-side Node.js code, so none of these
endpoints can exist on the current hosting.

## Decision

We will configure Astro with the `@astrojs/node` adapter in standalone mode and
`output: 'server'`, so pages are rendered on demand for each request.

- The app will be packaged as a Docker container and run on a container platform, with `/api/health` used for health checks.
- The existing S3 + CloudFront static site stays live alongside the container.

## Consequences

**Positive**

- API routes and health checks become possible.
- Pages can be rendered per request, which is the groundwork for content that
  changes dynamically.
- The same container runs locally and in AWS.
**Negative**

- Needs always-on compute, which costs more than serving files from S3.
- More to operate. A server can crash or hang, so it needs health checks, logs and
  restarts. A static site has none of these failure modes.
- Responses are slower than files cached at CloudFront's edge.

**Limitation**

Posts are still Markdown files loaded when the site is built. Rendering per request
does not by itself make a new post appear without a redeploy. Publishing posts
without redeploying requires loading them from a runtime source (a database, an API,
or live content collections), which will be a separate ADR.
